# スペックはどのように機能するのか？
**仕様書は**人間が理解しやすいように設計されている。  
しかし、**仕様書は**また、コンピュータ・ソフトウェアがあいまいさのない情報要件を自動的かつ正確にチェックできるよう、高度に構造化されている。  
すべての**仕様**書には3つの主要部分がある：

1. **説明**：**仕様の**根拠とその達成方法の説明。  
  この一部の部分は、人間が読んで、なぜ情報が要求されているのかを理解できるように設計されている。

  このフィールドはまた、様々な適用可能性ファセットの根拠を説明するために使用され、それらが個々ではなく、全体として資産に関連するデータ契約を識別するためにどのように役立つかを説明するために使用される。逆に、各要件ファセットの`description` データは、ユーザが必要とされる個々の情報の目的を理解するのに役立つはずです。

1. **適用可能性**：指定しようとしているモデルのサブセットを特定する。  
  IFC モデルにはさまざまなタイプのオブジェクトがあるが、**各仕様が**適用されるのはその一部だけである。  
  サブセットは、エンティティ（例：壁、窓）、クラシフィケーション（例：ユニクラスEF_25_10_25 外壁）などの利用可能なファセットを介して識別することができる。
1. **要求事項**：要求される特性や材料など、適用性で特定されたサブセットに対して要求される情報。

例えば、"*すべての壁が耐火等級を持たなければ*"ならないという**仕様は**、次のような構造になっている：

 1. **説明**: 建築基準法に準拠するためには、壁の耐火等級が重要である。

 1. **適用性**：この仕様は、すべての壁面に適用される。

 1. **要件**：前述の壁対象物は、耐火等級を有していなければならない。

## 仕様書は情報をどのように記述できるか
**適用可能**性と**要件は**、**Facets（ファセット）**コレクションを使用して記述されます。**ファ**セットは、モデル内の単一のエンティティ（壁、ドアなど）が持つ可能性のある情報を記述します。  
**ファセットは**、固定された**ファセット・パラメーターを用いて**情報を正確に記述するため、コンピューターはあなたが求めている情報を正確に理解することができる。

**ファセットが** **適用性の**セクションで使用される場合、モデルの関連部分を特定するために使用する情報が記述される。

**Facetが** **Requirements**セクションで使用される場合、モデル部品が**仕様に**準拠するために満たさなければならない情報制約が記述される。

| ------------------ | ----------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |

| **分類** | ** **システムと** 価値** | ユニクラス2015で"次のように分類される要素に適用される。 "EF_25_10_25" | ユニクラス2015の"分類基準を持っていなければならない。 "EF_25_10_25" |

**適用性**または**要件の**セクションで複数の**ファセットを組み合わせて**、さまざまな**仕様を**記述することができる。  
一部の**ファセットには**、オプションの**ファセット・パラメータが**あります。  
例えば、あるプロパティが存在することを指定したいが、正確な値は指定したくない場合、**プロパティファセットの**valueパラメータを省略することができます。

**ファセット・パラメータによっては**、有効な値のリスト、数値の範囲、テキスト・パターンを指定することもできます。これらは**複合制限と**呼ばれます。  
例えば、**複合制限を**使用して、火災評価プロパティが値"0HR、"1HR"、または"2HRの"いずれかからのみ選択しなければならないことを指定する。

## カーディナリティ
### 適用可能エンティティのカーディナリティ
**各仕様書では**、適用基準に合致するモデルのサブセットが、**必須（Required）**、**任意（Optional）**、または**禁止（Prohibited）**であることを定義している。  
次のような例がある：

```txt
applicability =  Type = walls 
                 Property = IsExternal
requirement   =  Property = FireRating
```

以下の解釈が適用される：

| <nobr>minOccurs</nobr> | <nobr>maxOccurs</nobr> | <nobr>解釈</nobr>             | <nobr>意味</nobr> |
| --------- | --------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1　　　　　　 | 無制限　　　　 | **必須**　　　　　 | IsExternalプロパティを持つ壁が、IFC モデル内に少なくとも1つ存在し、そのような壁がそれぞれ耐火等級プロパティを持っていなければ*ならない*。 |
| 0 | 無制限 | **任意** | IsExternalプロパティを持つ壁は、モデル内の*オプションで*あり、そのような壁が存在する場合、それらはすべて耐火等級プロパティを持っている必要があります。 |
| 0 | 0 | **禁止** | IsExternalプロパティを持つ壁がモデル内に見つかってはならない。 |

### 要件のカーディナリティ
個々の要件ファセットは、**必須**、**オプション**、または**禁止を**指定することもできます。

次のプロパティのような例がある：

```txt
Requirement 1: Property
    propetySet: ePset_SpaceOMA 
    property: TravelDirection
    datatype: IFCLABEL
```

以下の解釈が適用される：

| <nobr>タイプ</nobr> | <nobr>意味</nobr> | 成功の<nobr>基準</nobr>    |
| -------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **必須**　　　　　 | モデルにマッチするプロパティが必要 | 一致するエンティティは、ePset_SpaceOMA/TravelDirectionプロパティがIFCLABEL 型で、NULL以外の値を持つ。 |
| **禁止** | 一致するプロパティがモデル内に存在しない | 一致するエンティティのePset_SpaceOMA プロパティセットに TravelDirection プロパティがない。 |
| **任意** | propertySet/propertyの期待値と値の制約は定義されていますが、オプションです。 | 一致するエンティティは、そのプロパティを持っていないか、持っていても期待されるデータ型と値である。 |

完全な例として、モデルに耐力壁が含まれないようにしたい場合、耐力壁**禁止（Prohibited**from being load-bearing）の壁エンティティに適用される**Required**指定があるかもしれない。

## IFC スキーマサポート
**各仕様**書は、適用するIFC スキーマを定義する。対応するIFC スキーマは以下の通り：

- IFC4X3_ADD2
- IFC4
- IFC2X3

IDS は、提供されたIFC モデルが有効なデータのみを含んでいると仮定する。モデルに構文エラーやIFC スキーマ検証エラーがある場合、モデルを検証できないことがある。  
作成されたIFCs が有効であることを確認するのは、IFC オーサリングソフトウェアの責任である。

## 制限事項
IDSの最初のバージョンは、IFC 、すべての分野に共通する基本的な情報と関係を対象としている。  
より高度な情報要件は、現在のところIDSの対象外である。  
例えば、ジオメトリ検査、計算値や動的値に依存する検査、IFC モデル外のデータを参照する検査、ドメイン固有のIFC 関係を使用する検査はできない。

ここでは、監査を支援する他のツールを必要とする高度な要件のタイプをいくつか紹介する：

- 構造梁とパイプがぶつからないこと
- すべての壁は敷地境界から3m離す必要がある。
- すべてのオフィススペースの合計面積が300m2以上であること。
- すべてのドアタイプの名前は一意でなければならない
- すべてのポンプは、指定されたサプライヤーとメーカーを持つ必要がある。
- すべてのエアハンドリングユニットには、トリガーイベントを割り当てたセンサーが必要です。
- 土曜日と日曜日は、すべての勤務スケジュールにおいて休日でなければならない
- 主要なソフトウェア・ベンダーは、全モデルを3分以内にロードしなければならない。
- モデル内の関連図面は、CDE の最新リビジョンと一致していなければならない。
- すべての鉄筋はパラメトリックな掃引ディスクとしてモデル化されるべきである。
- 模型は建設時の状態と一致していなければならない。
