# 開発者ガイド
IDS ファイルは単なる XML ファイルであり、そのスキーマは XSD で定義されている。既存の IDS ファイルを開き、その内容を検査することで、IDS がどのような構造になっているかを知ることができます。

IDS は、XSD ベースの検証チェックに合格すれば有効であるとみなされます。公開IDSテンプレートのbuildingSMARTディレクトリで利用可能なすべてのサンプルIDSファイルは、有効であることが保証されています。

1. [最新のIDS XSDスキーマをダウンロードする](../../Schema/ids.xsd)

1. `Documentation/ImplementersDocumentation/TestCases` フォルダからサンプル IDS ファイルをダウンロードする。

XSDの検証を実行できる、自由に利用できるオンラインツールやプログラミングライブラリは数多くあります。  
buildingSMARTは、作成または受信したIDSファイルが完全に有効であることを確認するための[IDS監査ツールを](https://github.com/buildingSMART/IDS-Audit-tool/)提供します。同じツールは[Xbim IDS監査サービスでも](https://www.xbim.it/ids)利用可能で、Webブラウザでローカルに実行され、IDSファイルをサーバーにアップロードすることはありません。

## オーサリングIDS
IDSファイルの読み取りとオーサリングのみを行うソフトウェアを作成する場合は、以下の条件を満たす**必要が**あります：

- すべての IDS ソフトウェアは、有効な IDS ファイルのみを読み書きしなければならない。不正な IDS ファイルを読み込むためにリカバリが必要な場合は、その問題と自動リカバリイベントをユーザーに通知する必要があります。
- 独自の拡張は認められない。IDSまたは関連するIFCモデルを補強するために補助システム（例：追加ロードされたメタデータ）を使用する場合は、それがIDSの外部であることを利用者に明らかにしなければならない。
- データの損失は発生しないものとする。IDSをロードし、IDSを保存する場合、IDSのすべての情報を保持しなければならない。データが変更されない限り、構文の細かい書式変更は許される。
- スキーマの`xs:sequence` におけるxmlエンティティの順序は、尊重されるべきである。このxml機能の使用は、ファイル間の内容の比較を簡単にすることを目的としている。

さらに、以下のような機能をユーザーに提供することも強く推奨する：

- ユーザーが**Entity Facet** にIFCクラスを記述する場合、インターフェースは、仕様のために選択されたIFCスキーマで有効なIFCクラス名に許容値を制限する必要があります。オートコンプリートを推奨します。
- ユーザーが**Entity Facetに**定義済みの型を記述する場合、インターフェースは指定されたIFCクラスに基づいて許容値を推奨する必要があります。ただし、ユーザーがカスタム定義済みタイプを記述できるようにする必要があります。オートコンプリートを推奨します。
- ユーザーがすでに**エンティティ・ファセットを**指定しており、**アトリビュート・ファセットを**作成する場合、インターフェースは、指定されたIFCクラスに基づいて許容値を制限する必要があります。また、インターフェースは、指定された属性名に基づいて正しいデータ型を使用するようにユーザーをガイドする必要があります。
- ユーザーがすでに**エンティティ・ファセットを**指定しており、**プロパティ・ファセットを**作成する場合、インターフェースは、指定されたIFCクラスと定義済みのタイプに基づいて、許可されるプロパティ・セットを推奨する必要があります。ただし、ユーザがカスタムプロパティセット名を記述できるようにする必要があります。標準化された（例えば、`Pset_` や`Qto_` ）プロパティセットが推薦された場合、インターフェースは、許容されるプロパティ名を制限し、使用される適切なデータ型を推薦する必要があります。
- **プロパティファセット**内のカスタムプロパティに文字列が指定されている場合、IfcLabelはデフォルトのデータ型であることが好ましい。
- **プロパティファセット**内のカスタムプロパティに整数が指定されている場合、IfcIntegerがデフォルトのデータ型であることが好ましい。
- **プロパティファセット**内のカスタムプロパティにfloatが指定されている場合、IfcRealがデフォルトのデータ型であることが好ましい。
- ユーザーが単位付きの値を指定する場合、変換ツールを提供し、ユーザーが希望する単位で IDS を記述できるようにする必要があります。
- また、スペルミスを防ぐために、分類リファレンスだけでなく、一般的に知られているシステムの標準化された分類名をあらかじめロードしておくこともできます。この[IFCディレクトリを分類システムに](https://github.com/Moult/ifcclassification)使用することもできます。
- ユーザーが**マテリアルファセットを**指名する場合、インターフェースはIFCが推奨するマテリアルのカテゴリ（'コンクリート'、'スチール'、'アルミニウム'、'ブロック'、'レンガ'、'石'、'木'、'ガラス'、'石膏'、'プラスチック'、土'のいずれか）を推奨する必要があります。
- 値を指定する場合、XML文字列（simpleValueとrestriction enumerationの場合）は、[DataTypeのドキュメントで](DataTypes.md)提示されている[正規表現に](DataTypes.md#xml-base-types)準拠する必要があります。

## IFCに対するIDSのチェック
IDSチェックを実装するソフトウェアは、`Documentation/ImplementersDocumentation/TestCases`フォルダにあるIFC/IDSペアのテストスイートに準拠**しなければならない**（[テストケースの文書を](TestCases/scripts.md)参照）。

さらに、以下のような機能をユーザーに提供することも強く推奨する：

- IDS の監査結果を BCF-XML 形式で保存するか、BCF-API を介して OpenCDE に接続することを意図しています。しかし、BCF でのこれらの結果のフォーマットと全体的な構造化は、現在指定されていません。
- ソフトウェアがIDS仕様で指定されたIFCバージョンを解析できない場合は、ユーザーにその制限を知らせるべきである。
- 要件がオプションであるが、代わりに必須であれば失敗する場合、チェッカーツールはエラーを記録してはならないが、補助的な警告や推奨を提供することができる。

### 精密
浮動小数点値は、`x * (1. - 1.e-6) - 1.e-6`と`x * (1. + 1.e-6) + 1.e-6` の間の（排他的な）範囲にある場合、数値`x` と等価であるとみなされる。

これは、精度を小さな単位から大きな単位まで拡大できるようにするための妥協であり、単純化である。

### 制限事項
XSDには、**合計桁**数と**端数桁数の**制限もある。これらは有用性が限られるため、IDS ではサポートされない。

### オプション
仕様は、モデル上の`applicability`必須一致に応じて、**Required**、**Optional**、または**Prohibited**に設定することができる。これはXSDの`minOccurs`、`maxOccurs`機能を使って表現されます。これらは以下の状態で表されます：


| オプション | minOccurs | maxOccurs |
| ----------- | --------- | --------- |
| 必須 | 1 | 無制限 |
| オプション | 0 | 無制限 |
| 禁止 | 0 | 0 |

`minOccurs`、`maxOccurs`他の構成は現在許可されていない。
